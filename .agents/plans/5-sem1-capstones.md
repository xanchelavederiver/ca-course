Status: **implemented** 2026-11-20; all five references, vectors, benchmarks and both PDF sets verified

## Goal

Add five semester 1 capstones of approximately equal workload. Each project must have four kinds of deliverable:

1. **Student task description:** `spec.tex` → `spec.pdf`; this is the only PDF given to students.
2. **Instructor theory refresher:** `refresher.tex` → `refresher.pdf`; a short, self-contained review of the theory, algorithms, correctness invariants, complexity and testing pitfalls. It is **not for students**.
3. **Instructor reference project:** a complete implementation under the same restrictions as the student solution, with unit tests against independent oracles.
4. **Instructor assessment assets:** deterministic tagged vectors, benchmarks, calibration notes and generated `requirements.tex` as in Plan 4.

The target is one month per project, approximately 10 hours per week and **35–42 hours total**. There are no optional extensions in the required specifications. Reference implementations cover every required item, but no removed or optional functionality.

## Common decisions and safeguards

- Student-facing and instructor-facing mathematical documents are in Russian; code and repository documentation are in English.
- Python/Sage built-in big integers may perform supporting arithmetic. An algorithm under study must be implemented by hand, and its corresponding Sage/Python built-in may be used only as an oracle.
- Factorizations needed for order computation, primitive-root checks and Korselt/liar calculations are supplied as inputs. Factorization is not an additional hidden project.
- No production-grade optimization is required. Benchmarks compare the required algorithms and establish reasonable correctness-oriented limits.
- Every project includes unit tests, intermediate traces, valid corner cases and a small benchmark. Invalid-input behaviour must be explicit where the input contract permits it.
- Vector generators use only the supplied deterministic RNG. Every vector has tags, and verifiers accept every mathematically correct answer rather than only the recorded expected answer.
- Requirements are measured on the reference implementation with the existing slack mechanism (default 10×); no numerical time limit is invented before calibration.
- LCG/LFSR recovery vectors guarantee a unique answer. General ambiguous LCG enumeration and short, non-unique LFSR observations are outside scope.
- The month estimates exclude optional work because the revised specifications contain no optional section.

## Instructor-only theory refreshers

Use `refresher.tex` with the existing `ca-capstone` class; do not introduce another LaTeX class. Reuse `\capstonetitle`, ordinary sections, `\capstonerefs` and the shared `ca-refs.bib` bibliography. Add a prominent first-page label:

> Теоретическая справка для преподавателя. Не выдавать студентам.

Each refresher should be short (approximately **3–6 pages**, not a replacement for lecture notes) and contain, as applicable:

1. definitions and notation used by the specification;
2. key identities and theorem statements needed to understand correctness;
3. compact pseudocode for every required algorithm;
4. invariants, complexity and parameter-selection rules;
5. valid corner cases and common implementation mistakes;
6. references with precise locators;
7. a final checklist connecting the specification to reference tests and benchmark size classes.

The refresher may explain the algorithms fully because it is instructor-only, but it should not discuss the reference project's file layout or reveal the seeded vectors. Only `spec.pdf` may be copied into a student handout or submission package. `refresher.pdf`, `reference/`, `vectors/` and `bench/` remain instructor-only.

## Project 1 — Fast multiplication

### Student specification

Require exactly:

- schoolbook multiplication and Karatsuba as baselines;
- one fixed Toom–Cook variant, Toom-3;
- linear and cyclic convolution;
- multiplication using FFT in an appropriate finite field;
- automatic transform-length and prime selection from the input sizes and coefficient bound;
- construction of the required root of unity and transform inverses;
- exact integer reconstruction;
- signs, zero, unbalanced operands, maximum carries and internal parameter-validation errors.

For transform length \(N\), the implementation must derive and check the coefficient bound, choose a prime \(p\) large enough for exact reconstruction and satisfying \(N\mid p-1\), and select a root of exact order \(N\). Library primality testing is allowed during the search for \(p\); transform construction and multiplication are the student's work. No complex floating-point FFT, separate Fermat/Mersenne NTT implementations, multi-modulus CRT or automatic algorithm-family selection.

### Reference, vectors and benchmarks

- Implement all multiplication methods without calling built-in whole-input multiplication. Supporting addition, shifts and modular arithmetic may use big integers; primitive fixed-width digit operations are allowed.
- Test every method against Python/Sage integer multiplication and against the other methods. Test transform roots and inverse transforms independently.
- Generate zero and signed inputs, equal and very unbalanced lengths, all-ones limbs, carry chains, inputs close to coefficient-bound transitions, cases requiring several candidate primes and non-power-of-two input lengths.
- Benchmark the methods over increasing bit sizes and record when finite-field FFT becomes competitive. Generate requirement macros for the largest required input class and per-method time limits.

### Refresher contents

Convolution and integer multiplication, Karatsuba/Toom recurrences and interpolation, roots of unity in a finite field, forward/inverse transforms, the coefficient bound and prime-search rule, exact-order root construction, complexity, and the most common carry/root/inverse-transform mistakes.

## Project 2 — Montgomery arithmetic and exponentiation

### Student specification

Require exactly:

- Montgomery reduction, multiplication and exponentiation for valid odd moduli;
- binary left-to-right exponentiation;
- \(q\)-ary and sliding-window exponentiation;
- fixed-base precomputation and its reuse across requests;
- operation counts and a systematic benchmark matrix covering methods, window sizes, fresh versus reused precomputation, and ordinary versus Montgomery modular exponentiation;
- traces sufficient to inspect REDC and exponent recoding.

No addition-chain construction or search. Define behaviour for modulus 1, even moduli, exponent 0, base 0, non-coprime bases and invalid window parameters.

### Reference, vectors and benchmarks

- Do not use `pow(base, exponent, modulus)` or a Montgomery library in the solver; use it only as the oracle. Supporting xgcd may be implemented in the reference or reused from its own tested utility.
- Test zero and one-bit exponents, bases larger than the modulus, non-coprime bases, modulus 1, even-modulus rejection, several \(R\) choices where the API permits them, and repeated fixed-base requests with changed bases to detect stale caches.
- Benchmark at several modulus/exponent sizes and window widths. Measure precomputation separately from per-exponent cost and derive separate fresh/reused requirement macros where useful.

### Refresher contents

The Montgomery representation \(xR\bmod n\), REDC's identity and bounds, computation of \(n'\), conversion to/from the Montgomery domain, binary/\(q\)-ary/window recurrences, precomputation formulas, expected squaring/multiplication counts, and cache/corner-case pitfalls.

## Project 3 — Euclid, orders and primitive roots

### Student specification

Require exactly:

- binary GCD;
- extended Euclid and modular inversion;
- batch inversion, with explicit behaviour for zero and non-unit inputs;
- CRT for pairwise-coprime moduli;
- Garner's algorithm;
- sequential order reduction and the product-tree method;
- primitive-root search modulo a prime using the supplied factorization of \(p-1\);
- intermediate traces for Euclid, CRT/Garner, order reduction and root verification.

Order computations are in \(\mathbb Z_p^*\) for prime \(p\), with the factorization of \(p-1\) supplied. Primitive roots are required only modulo primes: no prime-power lifting, \(2p^k\), non-existence classification, rational reconstruction, general non-coprime CRT or enumeration of all roots.

### Reference, vectors and benchmarks

- Do not call Sage's `gcd`, `xgcd`, `inverse_mod`, `crt`, `multiplicative_order` or `primitive_root` in the algorithms under study; use independent implementations as oracles.
- Test even/odd and common-power-of-two GCD inputs, negative xgcd inputs, non-invertible elements, batch inputs containing zero or several non-units, permuted CRT residues, duplicate factors in \(p-1\), proper divisors as element orders and roots larger than 2.
- Verify a primitive root by both the defining order criterion and an independent oracle. Accept any correct primitive root, not only the smallest one.
- Benchmark small and large prime-power factorizations of \(p-1\), comparing sequential and product-tree order methods; benchmark batch inversion against repeated inversion.

### Refresher contents

Binary-GCD invariants, Bézout coefficients, prefix-product batch inversion and its failure cases, CRT and Garner recurrences, order reduction by prime divisors, the product-tree descent and leaf sequences, the primitive-root criterion, complexity and trace-checking invariants.

## Project 4 — Primality testing

### Student specification

Require exactly:

- Wilson's test as a correctness baseline without a performance requirement;
- Fermat and Miller–Rabin tests;
- Solovay–Strassen with an independently implemented Jacobi symbol;
- Korselt's criterion, including non-squarefree counterexamples;
- Fermat-liar counting for squarefree inputs with the factorization supplied;
- Lucas–Lehmer using Mersenne reduction rather than division by the Mersenne number;
- witness output, reproducible random bases and a comparison suite containing Carmichael, strong-pseudoprime, Euler-pseudoprime and Mersenne-composite cases.

No additional certificate systems or primality tests. Do not silently turn a probabilistic pass into a proof of primality in the API or traces.

### Reference, vectors and benchmarks

- Do not use Sage's `is_prime`, Jacobi symbol or Lucas–Lehmer implementation in the solver; use them only as oracles. Ordinary supporting modular exponentiation is allowed.
- Include small primes/composites, 1 and even inputs, Carmichael numbers, strong and Euler pseudoprimes for selected bases, non-squarefree numbers satisfying the Korselt divisibility conditions, Mersenne primes and composites, and fixed-seed reproducibility checks.
- Verify every reported witness independently. For squarefree inputs, check the liar count using \(\prod_{p\mid n}\gcd(n-1,p-1)\).
- Benchmark Miller–Rabin/Solovay–Strassen round counts and Lucas–Lehmer separately. Exclude Wilson from performance requirements and record that decision in `bench/README.md`.

### Refresher contents

Fermat's little theorem and liars, strong-probable-prime decomposition, Euler's criterion and Jacobi symbols, error bounds and witnesses, Korselt's criterion and the liar-count formula, Lucas–Lehmer recurrence, fast Mersenne reduction, and probabilistic-versus-deterministic verdict wording.

## Project 5 — LCG/LFSR cryptanalysis

### Student specification

Require exactly:

- LCG generation, period computation and full-period criteria;
- state recovery with known parameters;
- parameter recovery from consecutive full outputs on uniquely recoverable instances;
- LFSR generation over GF(2) and recurrence/polynomial conversion;
- Berlekamp–Massey and recovery from at least \(2L\) output bits;
- prediction and stream decryption;
- tests for degenerate recurrences, non-maximal periods and non-invertible LCG parameters where applicable.

Recovery inputs outside the uniqueness contract may be rejected, but no ambiguous-answer enumeration or short-observation non-uniqueness analysis is required. No truncated-output attacks, combined generators or correlation attacks.

### Reference, vectors and benchmarks

- Implement Berlekamp–Massey and the recovery logic directly; do not call Sage's Berlekamp–Massey or LFSR helpers in the solver.
- Use independent recurrence simulation, linear algebra or Sage as the oracle. Check predictions and decryptions by regenerating the stream.
- Generate full and non-full-period LCGs, non-invertible multipliers where the operation remains defined, known-state and uniquely recoverable unknown-parameter cases, zero/degenerate LFSR states, non-primitive recurrences and lengths both at and above \(2L\).
- Reject malformed or out-of-contract ambiguous instances explicitly, but do not generate them as required recovery tasks.
- Benchmark by modulus size, period-search bound and LFSR length; keep sizes small enough that period computation remains a reasonable one-month exercise.

### Refresher contents

The LCG recurrence and Hull–Dobell full-period conditions, period bounds, difference equations for full-output recovery, LFSR recurrence and connection/characteristic polynomials, linear complexity, Berlekamp–Massey invariants, why \(2L\) observations suffice in the unique case, and XOR stream encryption/decryption.

## Risks and controls

- **Scope creep breaks workload equality.** Treat the required lists above as maxima, not minima. Re-review the 35–42 hour budget at M5.
- **FFT parameter selection can hide incorrect reconstruction.** Unit-test the coefficient bound, root order and inverse transform independently, and include prime-transition vectors.
- **Montgomery benchmarks can be dominated by precomputation.** Report fresh and reused costs separately.
- **Mathematically invalid edge cases can become accidental requirements.** Keep supplied-factorization and unique-recovery contracts explicit in both spec and vectors.
- **Probabilistic tests can overstate certainty.** Require verdict/witness wording that distinguishes a probable prime from a proven prime.
- **Instructor material can leak into student handouts.** Use the separate `refresher.pdf` name, prominent Russian warning and an explicit bundle inspection at release.
